From "build failed" to root cause without scrolling 4,000 lines.

ci-triage parses a Jenkins, GitHub Actions or xcodebuild log, classifies the failure with fast rules, and points at the failing lines with a suggested fix. An LLM fallback is optional and only for the logs the rules cannot place.

Rules read patterns in the text. A log in a format they do not know comes back as unknown with low confidence, which is the case the optional LLM fallback is for. The flaky-test tracker needs a database, so it is CLI-only.

How it works

Fast and free first. The model is the exception, not the default.

1

Parse

A parser per CI source turns the raw log into entries and pulls out the lines around the failure, so the classifier sees the part that matters.

2

Classify by rule

Weighted patterns map the failure to a category with a confidence score, a summary and a fix. It takes milliseconds and costs nothing.

3

Escalate only if unsure

Below the confidence threshold, --llm sends the excerpt to Claude. Output stays in the same shape. In gate mode it exits 1 so the pipeline stops.

Use it in your pipeline

Python 3.11 or later, standard library only.

pip install git+https://github.com/gerardrecinto/ci-triage

ci-triage analyze build.log --source jenkins
ci-triage analyze - --source github   # stdin
ci-triage analyze build.log --source jenkins \
  --output json --exit-code
# low-confidence logs only
export ANTHROPIC_API_KEY=...
ci-triage analyze xcbuild.log \
  --source xcodebuild --llm

ci-triage flaky   # recurring test failures

Output can go to the terminal, JSON for dashboards, or a Slack webhook.

What this does not do
  • It does not fetch logs from your CI server. You pass it the log.
  • It names the most likely cause from patterns. It does not prove it.
  • Confidence is a rule weight, not a calibrated probability.
